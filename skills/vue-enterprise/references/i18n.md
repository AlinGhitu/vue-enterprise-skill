# Internationalization, dates and time

Source tags: [GL] GitLab (externalization, date and time guides) · [CB] open-source codebases (all five use i18n with one source locale) · [docs] MDN `Intl`, vue-i18n.

Retrofitting i18n into a large app is expensive. If the app might ever be translated, externalize strings from the start. When the project already has i18n, all new user-visible text goes through it.

## Strings [GL, CB]

- Every user-visible string goes through the i18n function, including `aria-label`, `title`, `alt`, placeholders, toasts and error messages.
- One source locale file (`en.json`) that developers edit; other locales come from translators.
- Pass the i18n function **literal keys or strings**, never variables or template literals. Extraction and missing-key checks are static.
- Type the keys: augment `DefineLocaleMessage` (and `DefineDateTimeFormat`, `DefineNumberFormat`) in `declare module 'vue-i18n'` with the source locale's shape (`typeof import('./locales/en.json')`), so `t('invoice.paidBy')` autocompletes and a removed key fails `vue-tsc`. It covers JSON messages only, not `<i18n>` SFC blocks.
- Never split a sentence across several translation calls, or build it by concatenation. Translate the whole sentence with named placeholders: `t('invoice.paidBy', { name })`. Word order differs between languages.
- Links or components inside a sentence use component interpolation (vue-i18n `<i18n-t keypath="…">` with named slots), with the link text itself translatable. Never put HTML in translation strings: translators can break it, and it's an injection vector.
- Plurals use the plural API (vue-i18n `t('items', count)` with plural forms in the message), never `count === 1 ? … : …`. Languages have more than two plural forms.
- Prefer one full string per case over a string with a variable noun; gender and grammatical case vary.
- Don't change case in code (`toLowerCase`, CSS `text-transform` on translated text); translators control it.
- Namespace keys by feature and context (`billing.invoice.actions.delete`), so translators have context and keys don't collide.
- Hoist a string to a constant only when it's reused, processed, or looked up at runtime (enum → label). Otherwise write the call inline.
- Tests assert the source-language text; don't wrap expectations in `t()`.

## Numbers, currency and dates [GL, docs]

- Format numbers, currency, percentages and dates with `Intl` (`Intl.NumberFormat`, `Intl.DateTimeFormat`, `Intl.RelativeTimeFormat`) in the user's locale, through one shared formatter module. Never hand-roll formats.
- `new Date('2026-09-19')` parses date-only ISO strings as **UTC** midnight, which shows the previous day in time zones west of UTC. Parse date-only values with an explicit local constructor (`new Date(y, m - 1, d)`), append a time (`'2026-09-19T00:00'`), or keep them as strings.
- Send date-only values to the API as `YYYY-MM-DD` strings, never serialized `Date`s.
- Test date logic with a fixed fake date, and check displays manually in a negative, zero and positive UTC offset.
- Server-rendered dates that differ on the client (relative times, the user's zone) get `data-allow-mismatch` (Vue 3.5) or render client-side only.

## Layout direction [CB]

- Use CSS logical properties (`margin-inline-start`, `padding-inline`, `inset-inline-end`; utility equivalents like `ms-2`, `pe-4`) instead of left/right, so right-to-left languages work without a separate stylesheet. Set `dir` on `<html>` from the locale.

## Loading [docs]

- Lazy-load locale messages per language (and per feature for very large apps), so users only download their own.
